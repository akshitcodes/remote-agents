System Architecture

Driving Codex from your phone

A single Node process on your Mac turns the Codex CLI into something you can open, read, and continue from your pocket — through verified HTTPS, protected by a long random pairing token.

The whole idea

One bridge, two protocols, one verified address

Your phone can't talk to the Codex CLI directly — the CLI speaks a machine protocol over pipes, not HTTP. So the bridge does two translations at once: it turns your phone's taps into JSON-RPC calls the CLI understands, and it turns the CLI's streaming output into a live feed the browser can render. Tailscale Funnel supplies encrypted public HTTPS without opening a router port or installing an app on the phone; the bridge still requires its pairing token.

On the wire

Commands go down, events come up

The connection is deliberately lopsided. Your actions are occasional, request-and-reply: tap a session, send a message. The agent's output is a continuous stream — reasoning, tokens, command results — that has to arrive as it happens. So the bridge uses two different channels, each suited to its direction.

↓ Phone → Mac

Discrete HTTP requests, answered once each.
  • thread/list  — browse sessions
  • thread/read  — load history
  • thread/resume — reopen a session
  • turn/start  — send a message
  • turn/interrupt — stop a run
  • approval  — allow / deny

↑ Mac → Phone

One long-lived stream (Server-Sent Events).
  • turn/started
  • item/agentMessage/delta
  • item/started  — command / edit
  • item/completed
  • requestApproval  — needs you
  • turn/completed

The stream is why replies type out live and approval prompts appear the instant the agent asks.

Trace · one sequence

Anatomy of a single message

Here is exactly what happens between tapping send and watching the reply appear.

  1. You tap send. The web app POSTs your text to /api/message with the session's id.
  2. Bridge reopens the session. If this session isn't live yet, it calls thread/resume — loading the exact rollout file from disk.
  3. Bridge starts a turn. It sends turn/start to the app-server over the pipe.
  4. The agent works. app-server calls the model, runs commands, edits files — emitting events the whole time.
  5. Events stream to your phone. Each delta is pushed down the open SSE channel; the reply grows character by character.
  6. Turn completes. A turn/completed event arrives, the input unlocks, and the change is already saved to the same file your Mac terminal reads.
🔒
Why this is safe to leave running. The Mac never opens a public port — the only way in is the Tailscale mesh, which requires your logged-in device. On top of that, every request needs the pairing token. The trade-off: whoever holds the pairing link can drive Codex as you, so treat it like a password and keep the bind on the tailnet, never 0.0.0.0 on a café network.
Where this goes next

From reading Codex to commanding every agent

Today the bridge does one thing well: your Codex sessions, on your phone. To make it a genuine control room — every agent on every machine, managed from your pocket — two things have to change. It has to speak to more than one agent, and it has to reach you instead of waiting for you to check it.

That second point is the real hinge. Right now you have to open the app to know anything happened. A control room pushes: "agent finished," "agent needs approval," "agent hit an error." Everything below is ordered by that leverage — the pieces that turn viewing into managing come first.

01

Always-on daemon

do firstsmall

A LaunchAgent plus caffeinate so the bridge starts on login, restarts if it dies, and keeps the Mac awake while a run is active. Without this, everything else is moot the moment the lid closes. This is an afternoon of work and I can set it up now.

02

Push notifications

high impactmedium

The feature that makes it manage. When a turn finishes or an approval is waiting, your phone buzzes. Cheapest path is a self-hosted push service (ntfy) the bridge posts to — works with the web app today, no Apple account. Richer path is native APNs, which needs the paid developer account.

03

Multi-agent adapters

high impactmedium

Wrap each CLI behind one interface — list, read, send, events — and normalize their output into a single event model. Codex is done; Claude Code (stream-json) and Cursor slot in next. t3code already solved this normalization in the open — worth borrowing its shape rather than reinventing it.

04

Orchestration dashboard

high impactmedium

A home screen listing every agent with a live status pill — running · idle · waiting on you · failed — plus the ability to start a fresh session with a project, model, and effort picker, and run several in parallel. This is the "control room" view the whole thing is building toward.

05

Multi-host + wake relay

mediumlarger

Point the phone at several machines at once — home Mac, work machine, a cloud box that never sleeps. A small outbound-dialing relay covers the cases Tailscale can't (a sleeping laptop, locked-down networks), and could even wake a host on demand before handing off the task.

06

Native iOS app

polishlarger

The original goal, once the web version proves the workflow. Background connections that survive a locked phone, real notifications, biometric unlock, and a share sheet to fling a link or snippet straight to an agent. Buildable with a free Apple account for personal sideloading; notifications are the reason to eventually pay the $99.

🧭
If you do nothing else, do 01 and 02. An always-on bridge that can buzz your phone is the difference between a clever demo and a tool you actually run your agents from. The rest is breadth on top of that foundation.
